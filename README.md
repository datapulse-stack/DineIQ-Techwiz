# DineIQ Analytics

**MenuMatrix Dining Intelligence — shipped under the Data Pulse brand.**

DineIQ takes a year of raw restaurant transactions and turns them into decisions:
which dishes actually make money, which ones only look busy, who's about to churn,
what to forecast, and what to do about all of it. It's built in Python, stores its
data as CSV, runs a real Apache Spark Big-Data track alongside a Python
Data-Science track, and serves everything through a Flask dashboard.

Everything you see is computed by our own code. There's no external "AI" API making
the calls at analysis or recommendation time.

---

## What it does

- **Cleans and integrates** 11 raw CSV tables into a single order-line fact table,
  quarantining bad data and logging every step.
- **Classifies every dish** into Profit Driver / Volume Driver / Hidden Opportunity
  / Low Performer — and the label is *location-specific*.
- **Runs two independent ML pipelines** (Spark MLlib + scikit-learn) and compares
  them head to head.
- **Forecasts demand** overall and per location/category, with honest held-out
  validation.
- **Segments customers** (RFM + K-Means), scores **churn risk**, mines
  **market-basket** bundles, analyses **pricing**, **promotions**, **wastage**,
  **anomalies** and **peak periods**.
- **Serves it all** through a role-aware dashboard with light/dark themes, CSV +
  Excel export, an in-app report viewer, a what-if simulator and a rule-based
  assistant.

Headline numbers on the bundled dataset: **$33.75M revenue**, **$18.27M profit**,
**312,502 orders**, **7.3% wastage**, forecast **MAPE 3.9% (R² 0.86)**, dual-pipeline
**agreement 95%**.

## Quick start

You need **Python 3.10+**. Spark is optional (see below) and only needed if you
want to run the Big-Data track yourself.

```bash
# 1. clone / unzip, then from the project root:
# Open the Final Day folder.
# Navigate to the Project folder.
# Open a terminal in the Project folder.
# Run the required command.
python -m venv .venv

# 2. activate it
#    macOS / Linux:
source .venv/bin/activate
#    Windows (PowerShell):
.venv\Scripts\Activate.ps1

# 3. install
pip install -r requirements.txt

# 4. generate the data + run the whole analytics pipeline (one command)
python run_all.py

# 5. start the dashboard
python app.py
```

Then open **http://localhost:5000** and log in:

| Role | Email | Password |
|------|-------|----------|
| Admin | `admin@dineiq.local` | `admin123` |

Change that password after first login (Admin console). New sign-ups land as
**Analyst** (read-only) until an Admin promotes them.

### Handy re-runs

```bash
python run_all.py --skip-gen     # keep the existing data, just re-run analytics
python -m src.make_splits        # (re)write processed_data/splits/{train,val,test}.csv
```

## Running the Spark Big-Data track (optional)

The Python pipeline in `src/` is the reference implementation the dashboard uses,
and it runs on any machine. The **Spark** pipeline in `spark_jobs/` is the separate
Big-Data track — it does schema-defined ingestion, Spark SQL joins, a partitioned
Parquet write, and three Spark MLlib models.

It needs a **Java 17+ JVM** and PySpark:

```bash
pip install pyspark
python spark_jobs/spark_pipeline.py
```

It writes:

- `processed_data/spark/fact_order_lines.parquet/` — partitioned by location
- `processed_data/spark_predictions.csv` — per item×location predictions
- `processed_data/spark_metrics.json` — the 3-model leaderboard
- `spark_jobs/models/spark_best_model/` — the saved MLlib model
- `spark_jobs/logs/spark_run.log` — the run log

Once those exist, the Python comparison in `src/models.py` automatically prefers
the real Spark predictions. If Spark isn't installed, it falls back to a second,
differently-configured Python model family as a clearly-labelled stand-in so the
comparison still runs — nothing is hidden.

## The two pipelines

The brief asks for two **independent** pipelines whose results are compared, so
that's exactly what this is:

- **Python DS** (`src/`) — pandas + scikit-learn. Trains a gradient-boosted
  machine, extra-trees and logistic regression; picks the best by macro-F1; saves
  the model.
- **Big Data** (`spark_jobs/`) — PySpark + Spark SQL + Spark MLlib. Trains Random
  Forest, Decision Tree and Logistic Regression on the same problem, independently.

They never share predictions. The comparison engine lines up both on 3,000
item×location cells and reports agreement and every disagreement, with the item,
location and each side's call. Disagreements cluster on the boundary cases — which
is exactly where two differently-built models *should* diverge.

## Tests

```bash
python -m pytest tests/ -q      # 18 tests
```

Covers six areas: functional (scale + integrity), data-quality + boundary (a frame
of injected defects the cleaner must catch — our hidden-defective-data readiness
check), integration (fact table reconciles), model (comparison coverage, ≥3 Spark
algorithms, saved models, forecast beats baseline), and security (hashing, auth
rejection, role permissions, password reset).

## How the classifier thinks (design notes)

- Demand and profitability are scored **relative to the whole menu**, then
  profitability is knocked down for wastage and weak ratings before bucketing. High
  sales alone never make a dish a winner.
- The class label is **location-specific** — same dish, different verdict per
  branch.
- Forecasting trains only on earlier days and validates on a held-out later window,
  benchmarked against a naive baseline to prove it adds value.
- The churn model deliberately **excludes recency** from its features, because the
  churn label is derived from recency (that would be leakage).
- Every recommendation carries its supporting evidence.
